01 / THE GAP

An insight that couldn't act on itself.

The Customer Segmentation page closed with a finding: walk-in customers dominate the mix, and converting frequent walk-ins into registered members was flagged as the opportunity. True — and useless in the same breath.

  • 169,244 of 225,499 payments (75%) came from Walk-In customers — no name, no history, nothing to recognize them by
  • Nothing in the schema linked one Walk-In visit to another, even when it was the same person
  • Cashiers rotate shifts, so even a genuinely familiar face went unrecognized visit to visit
Strategic Focus

Stop asking how many walk-ins exist, and start asking which one just paid — and whether it's happened before.

02 / IDENTITY RESOLUTION

Turning a discarded signal into a detector.

A transfer payment already carries the sender's name — a piece of identity the business was collecting and immediately throwing away. Two honest iterations got this right.

  • Enriched 101,463 Walk-In transfer payments with realistic payer identities, drawn from a Nigerian name library spanning Yoruba, Igbo, Edo, Efik/Ibibio and Urhobo/Isoko names
  • Built a fuzzy identity resolver with rapidfuzz, blocked by surname so each name is only compared against plausible matches
  • Added Payer_Name to FactPayments as an additive change — nothing in the existing schema was altered
Strategic Focus

The data needed to recognize repeat customers was already there — collected at every transfer, then thrown away.

UNDER THE HOOD

How a transfer name becomes an identity.

Bank transfer names are messy: inconsistent casing, reordered names, stray punctuation. The resolver has to see through that noise without inventing matches that aren't there.

  1. Normalize Lowercase, strip punctuation, collapse spaces, then sort the name tokens so word order stops mattering. ADEGBITE, Femi → adegbite femi
  2. Block Group names by surname. A name is only compared with others in its block, which keeps matching fast across 101,463 payments.
  3. Score Measure similarity inside each block with a token-sort ratio from rapidfuzz.
  4. Guard Require an exact token match on top of the score, so near-identical first names never merge.

Two honest iterations

Both bugs were caught before any number on this page was reported. Neither would have been visible on a dashboard.

Iteration 1 · Data enrichment

Names that collided

What went wrong
The first version drew payer names with replacement, so different customers at the same branch could be handed the same name — manufacturing repeat visitors who didn't exist.
The fix
Names are now drawn without replacement within each branch, so every distinct customer keeps a distinct identity.

Iteration 2 · Identity resolution

Names that merged

What went wrong
An early, loose similarity threshold treated "Femi Adegbite" and "Yemi Adegbite" as one person — two real customers collapsed into one.
The fix
The resolver was tightened to require an exact token match, so a high similarity score alone can no longer merge two people.

03 / VALIDATED DETECTION

A rule you can check, scored against the truth.

A detection rule is only as good as the evidence behind it. Because every payer identity in the dataset was generated, the genuine repeat customers were known in advance — so the rule could be scored, not just trusted.

The detection rule
FOR EACH resolved payer at a branch
  visits    = count of transfer payments
  avg_spend = mean payment amount

FLAG AS retention candidate
  WHEN visits    >= 2
   AND avg_spend >= the branch's own average
Two conditions, both explainable to a branch manager in one sentence. Nothing to defend as a black box.
100%

Precision

Every customer the rule flagged was a genuine repeat, above-average spender. Zero false alarms.

88.3%

Recall

Of all the genuine repeat, above-average spenders in the data, the rule found 88.3%.

Why precision matters most here

An alert that names the wrong customer costs a manager's trust, and a manager who stops trusting alerts stops reading them. A missed customer costs less — they walk back in, and the next visit is another chance.

What the 11.7% gap means

Some genuine repeat customers weren't flagged. It's reported as-is: a detector that misses a few customers but never invents one is the right failure mode for a first deployment.

Why the two fixes came first

Colliding names would have corrupted the ground truth itself, and merged names would have blurred who counts as a repeat customer. Validation only means something once the identities underneath it are right.

04 / FROM DETECTION TO ACTION

A validated rule is only useful if someone sees it.

Two layers sit on top of detection, aimed at two different moments in the business — the next morning, and the next visit.

  • A Python service re-runs detection and sends each branch a digest over Telegram and email — 3,645 candidates on the first run, delivered as a handful of messages, not 3,645 pings
  • RetentionAlertsSent records every customer already announced, so each new digest only carries who's new
  • Credentials live in their own config file, never in the script — adding a recipient never means touching code
Strategic Focus

A digest is useful the next day. Recognition at the till is powerful the moment it happens.

How each run avoids repeating itself

Detection runs again and again, but a manager should only ever hear about a customer once.

  1. Detect Re-run the rule against the latest payments in SQL Server.
  2. Compare Check every candidate against RetentionAlertsSent.
  3. Send Group only the new candidates by branch and send one digest per branch.
  4. Record Write each announced customer to RetentionAlertsSent so they're never announced twice.
A real digest arriving on Telegram.
05 / RECOGNITION AT THE TILL

Five seconds at the till. No POS changes.

Cashiers rotate shifts, so the person who remembers a customer is rarely the one serving them. The till-side companion gives every cashier the same memory: type the name on the transfer and get an instant read.

  • New No record of this name yet. Record the visit so the next cashier sees it.
  • Returning Has paid here before. Greet them back.
  • Retention candidate Two or more visits at or above the branch's average spend. Invite them to register.

The simulator runs in your browser with sample customers and a demo branch average of ₦18,500. The real app is a Flask service backed by a SQLite database shared by every till in the store.

DECISIONS & TRADE-OFFS

The choices that shaped it.

Every system is a set of trade-offs. These are the ones that mattered most, and why each went the way it did.

Standalone at the till, not built into the POS

Instead of integrating with the store's point-of-sale system

Touching a store's POS means vendor involvement and head-office IT approval. A standalone tool can be trialled at a single branch without anyone else's sign-off, and removed just as easily.

One digest per branch, not one alert per customer

Instead of a notification for every candidate

3,645 candidates on the first run would have been 3,645 notifications. Batched by branch, it becomes a handful of messages a manager will actually read.

Zero false alarms over maximum coverage

Instead of a looser rule that catches more and gets some wrong

Trust is the scarce resource. The rule runs at 100% precision and reports its 88.3% recall openly, rather than trading a manager's confidence for a bigger number.

An additive schema change

Instead of restructuring FactPayments

Payer_Name was added as a new column and nothing existing changed, so nothing Version 1 depends on had to be rebuilt.

SQLite at the till, SQL Server for analytics

Instead of every till querying the warehouse

The two pipelines never depend on each other. The till tool keeps working even in a store the analytics stack doesn't reach.

Credentials in config, not in code

Instead of tokens and passwords inside the script

Adding a manager or rotating a password is a config edit, and secrets stay out of the script that gets shared and versioned.
